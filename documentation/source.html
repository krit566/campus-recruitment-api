Overview

A REST API for a college placement cell: students, companies, job postings and applications. Beyond basic create/read/update, it enforces the rules a real placement process depends on (eligibility, an application workflow, an offer limit) and it stays correct when things go wrong: clients retry, two reviewers click at the same moment, a student tries to act as someone else.

One application per student per job is a database UNIQUE constraint, so it holds even when two requests arrive together; a Python check alone could be raced.

Reliability

Retries: idempotency keys

A client that times out cannot know whether its request worked. With an Idempotency-Key, the first response is stored and a retry gets the same response back (Idempotent-Replayed: true) instead of acting twice. Reusing a key with a different body is rejected (422); failed requests are not stored, so a corrected retry still works. Payment APIs require the same pattern.

Races: the last opening

change_status reads the application, checks "offers left?" and writes inside one BEGIN IMMEDIATE transaction, which takes SQLite's write lock before reading. The second reviewer therefore sees the first offer and gets 409. The update is also compare-and-set (WHERE status = <status we read>). tests/test_concurrency.py fires 8 parallel offers at a job with one opening and checks that exactly one wins.

Writing that test found a real bug: the database connection was opened on one worker thread and used on another, which SQLite refuses by default. The fix and the reasoning are in app/db.py.

Limitations and next steps

  • Idempotency is checked before and stored after the action, outside one transaction: two simultaneous first attempts with the same key could both run (the UNIQUE rule still blocks a duplicate application). Fix: reserve the key in the same transaction.
  • Key rotation and expiry; per-key rate limiting.
  • Migrations (Alembic) and PostgreSQL for several instances, with row locks (SELECT … FOR UPDATE) instead of SQLite's single write lock.
  • Export metrics to Prometheus instead of in-process counters.

Interview questions

Why a database constraint and not only a Python check for duplicates?
Two requests can both pass the Python check before either inserts. The constraint is enforced by the database at write time.
Why BEGIN IMMEDIATE instead of BEGIN?
A plain BEGIN takes the write lock only at the first write, so two transactions could both read "1 offer left". IMMEDIATE locks before the read.
422 vs 403 vs 404 vs 409?
Malformed input; allowed input but a rule forbids it; record missing; request conflicts with the current state.
Why store API keys hashed and compare in constant time?
A leaked database does not leak usable keys; constant-time comparison stops timing attacks from guessing a key byte by byte.
What does an idempotency key protect against?
A client retrying after a timeout and causing the action twice: a second application, a second status change, or in payments a second charge.
