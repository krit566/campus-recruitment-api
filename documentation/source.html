Overview

PlaceRight is a full-stack campus placement portal. Students sign up with their college email, see only the jobs they are eligible for, apply once and follow each application from "applied" to "offered". The placement office verifies CGPAs, posts jobs, moves applicants through a kanban pipeline, books interview slots without clashes and exports applicant lists. Beyond create/read/update, it stays correct when things go wrong: clients retry, two reviewers click at the same moment, two officers book the same panel, a student tries to act as someone else.

Concurrency and retries

The last opening

change_status locks the job row with SELECT ... FOR UPDATE before reading anything, then locks the application. A second reviewer's transaction waits on the job lock, then sees the first offer and gets 409. The update is also compare-and-set (WHERE status = <status we read>). Locks are always taken job first, then application, so two transactions can never wait on each other in a circle (no deadlock). Applying takes a FOR SHARE lock, so many students can apply at once but a job cannot be closed in the middle of an application.

Idempotency keys

The first version (SQLite) stored the key after the action, so two simultaneous first attempts with the same key could both run. Now the key is reserved first, in the same transaction:

sequenceDiagram participant A as Request 1 (key k) participant B as Request 2 (key k) participant D as PostgreSQL A->>D: INSERT key k (reserved, not committed) B->>D: INSERT key k Note over B,D: waits on request 1's row A->>D: apply, store response, COMMIT D-->>B: conflict: key exists B->>D: SELECT stored response B-->>B: replay it (Idempotent-Replayed: true)

If request 1 fails, its reservation rolls back with it and request 2 runs normally, so a corrected retry works. A test sends 8 simultaneous first attempts with one key: one application is created and 7 responses are replays.

Interview clashes

"Check for an overlap, then insert" is a race. schedule_interview locks the student's row and takes a per-panel advisory lock (pg_advisory_xact_lock(hashtext(lower(panel)))), in that order, before checking and writing. A test books one panel for six students in parallel: exactly one succeeds. (A Postgres exclusion constraint on time ranges would be the database-level alternative; it needs the btree_gist extension.)

Web app

  • One API client (api.ts) adds the token, turns error responses into readable messages and signs the user out when a session expires.
  • Each "Apply" or status change gets an Idempotency-Key; retrying the same action reuses it.
  • The kanban asks the API which moves are allowed (/meta/workflow) and shows only those; the API still checks every move.
  • Accessibility: labelled fields, focus moved to the page heading after navigation, a skip link, live-region announcements on the board, keyboard-usable buttons for every drag-and-drop action, AA-contrast status colours; axe-core runs in the tests.
  • Responsive down to 375 px: the kanban columns stack and wide tables scroll inside their card, so the page never scrolls sideways.

Limitations and next steps

  • The token lives in sessionStorage: simple, but readable by any XSS. An HttpOnly cookie with CSRF protection is stronger.
  • Login lockout and metrics are in memory (per instance); several instances would use Redis or the database, and Prometheus.
  • No email verification, password reset or refresh tokens yet.
  • Resumes are on a local volume; Render's free tier has no persistent disk, so object storage is the real fix.
  • Notifications are in-app only.
  • Demo data is generated and fictional; there are no real usage figures.

Interview questions

Why lock the job row and not just check the offer count?
Two transactions can both read "1 opening left" before either writes. FOR UPDATE makes the second wait until the first commits, so it reads the new count.
Why reserve the idempotency key before doing the work?
Inserting the key first makes Postgres serialise requests with the same key: the second waits on the first's uncommitted row, then replays its response. Storing it afterwards leaves a window where both run.
Why is a UNIQUE constraint still needed?
Application code checks can be raced; the database enforces the rule at write time no matter how requests interleave.
Why bcrypt for passwords but SHA-256 for API keys?
Passwords are short and guessable, so hashing must be slow. API keys are long random strings, so a fast hash is enough.
What stops a forged token?
The signature is checked with the server's secret and only HS256 is accepted, so a token signed with another key (or with "none") is rejected.
401 vs 403 vs 409 vs 422?
Not signed in; signed in but not allowed; conflicts with the current state; the request itself is invalid.
